## 1. はじめに

### 1.1 目的

本書類は、トピックごとにニュースを集め、AI 要約と重要度付きで読む Web アプリ「ニュースデスク」の**基本設計**をまとめたものです。

たとえで言うと、「どんなお店を作るか・店と倉庫と配達の役割分担」を決める設計図です。部品のネジ一本までの細かい仕様は、別紙の詳細設計書を参照してください。

### 1.2 対象読者

- 本システムの開発・運用に関わる人
- ソースコードの全体像を先に把握したい人

### 1.3 用語

| 用語 | 意味（簡単なたとえ） |
|------|----------------------|
| トピック | 話題のラベル（例: 人工知能）。新聞のコーナー名 |
| 記事 | 1本のニュース。倉庫の1箱 |
| RSS | サイトが公開する新着一覧の配信口。速報ボード |
| キュレーション | RSS を集め、要約・重要度を付けて保存する一連の作業 |
| anon key | ブラウザ用の入場券（公開してよい鍵） |
| service_role key | 倉庫のマスターキー（バックエンド専用・秘密） |
| RLS | Supabase の行単位の門番（誰が読んでよいかの許可） |

## 2. システム概要

### 2.1 何をするシステムか

1. ユーザーがトピック（話題）を登録する  
2. トピックに紐づく RSS から記事を取得する  
3. AI が要約と重要度（高／中／低）を付ける  
4. Supabase に保存する  
5. 画面で未読中心に読み、既読にできる  

### 2.2 全体構成

```text
[ブラウザ]
    │
    ├─(表示・トピック追加・既読・今すぐ取得)─→ [frontend: Next.js]
    │                                              │
    │                                              ├─ anon key ──→ [Supabase]
    │                                              │                   ↑
    └──────────────────────────────────────────────┴─ POST /jobs/curate
                                                       │
                                               [backend: FastAPI]
                                                       │
                         ┌───────────┬─────────────────┼─────────────────┐
                         ▼           ▼                 ▼                 ▼
                      [RSSサイト] [OpenAI API]   [Supabase]
                                              (service_role)
```

### 2.3 役割分担

| 役割 | 担当 | たとえ |
|------|------|--------|
| 画面表示・トピック追加・既読 | `frontend/` | 新聞売り場のカウンター |
| RSS 取得 | `backend/` | 配達員 |
| AI 要約・重要度 | `backend/` | 編集部 |
| 記事の書き込み（INSERT） | `backend/` → Supabase | 倉庫への入庫 |
| 記事の表示・既読更新 | `frontend/` → Supabase | 倉庫から客に見せる／読んだ印 |

**方針:** 画面の読み取りはフロントが Supabase に直接接続する。重い収集・要約・入庫はバックエンドが行う。

## 3. 技術スタック

| 層 | 技術 | 備考 |
|----|------|------|

## 4. 機能一覧

### 4.1 フロントエンド機能

| ID | 機能名 | 概要 | 優先 |
|----|--------|------|------|
| F-01 | トピック一覧表示 | 左ペインにトピックを表示 | 必須 |
| F-02 | トピック追加 | 名称を入力して `topics` に INSERT | 必須 |
| F-03 | トピック選択 | 選択トピックの記事を右ペインに表示 | 必須 |
| F-04 | 記事タイムライン | カードでタイトル・公開日・要約・重要度を表示 | 必須 |
| F-05 | 重要度バッジ | high=赤 / medium=黄 / low=グレー | 必須 |
| F-06 | 既読化 | `is_read=true` に更新し、既定では非表示（またはグレー表示切替） | 必須 |
| F-07 | 既読の表示切替 | 「既読を表示／隠す」 | 必須 |
| F-08 | 今すぐ取得 | RSS URL を指定しバックエンドのキュレート API を呼ぶ | 必須 |
| F-09 | RSS URL 記憶 | トピックごとのフィード URL をブラウザ localStorage に保存 | 暫定 |

### 4.2 バックエンド機能

| ID | 機能名 | 概要 | 優先 |
|----|--------|------|------|
| B-01 | ヘルスチェック | `GET /health` で稼働と設定有無を返す | 必須 |
| B-02 | 手動キュレート | `POST /jobs/curate` で RSS→AI→DB を実行 | 必須 |
| B-03 | RSS 取得 | フィード XML を取得し記事候補に変換 | 必須 |
| B-04 | AI 要約・重要度 | OpenAI で summary / importance を生成 | 必須 |
| B-05 | 重複排除 | 同一トピック内の既存 URL を除外 | 必須 |
| B-06 | 記事 INSERT | `articles` へ書き込み（`is_read=false`） | 必須 |
| B-07 | CORS | フロント（既定 `localhost:3000`）からの呼出を許可 | 必須 |

### 4.3 対象外（現状）

| 項目 | 状態 |
|------|------|
| ユーザー認証・マルチテナント | 未実装（開発用に広い RLS を想定） |
| 定期自動取得（cron 等） | 未実装（手動 API のみ） |
| `topics.feed_url` の DB 永続化 | 未実装（localStorage 暫定） |
| 記事削除・トピック削除 UI | 未実装 |

## 5. 画面設計（概要）

### 5.1 画面構成

1画面構成のダッシュボード（ルート `/`）。

| 領域 | 内容 |
|------|------|
| ヘッダー | ブランド名「ニュースデスク」 |
| メッセージ帯 | 設定不足・取得結果・エラーの案内 |
| 左ペイン | トピック一覧 ＋ 新規トピック追加フォーム |
| 右ペイン | 選択トピックの記事一覧 ＋ RSS URL ＋「今すぐ取得」 |

### 5.2 画面遷移

単一ページのため画面遷移はなし。トピック選択と取得ボタンで右ペインの内容が更新される。

### 5.3 主要操作フロー

#### （1）記事を読む

1. 左でトピックを選ぶ  
2. 右に未読記事が並ぶ  
3. タイトルから元記事へ遷移（別タブ）  
4. 「既読にする」で未読一覧から外れる  

#### （2）今すぐ取得

1. トピックを選ぶ  
2. RSS URL を入力（ブラウザに記憶）  
3. 「今すぐ取得」を押す  
4. バックエンドが収集・要約・保存  
5. 画面が記事一覧を再読込

## 6. データ設計（概要）

### 6.1 ER 概要

```text
topics 1 ─────< articles
  id                 id
  name               topic_id (FK)
  created_at         title, url, summary,
                     importance, is_read,
                     published_at
```

### 6.2 テーブル概要

#### topics（話題）

| 列 | 型（想定） | 説明 |
|----|------------|------|
| id | uuid / text | 主キー |
| name | text | トピック名 |
| created_at | timestamptz | 作成日時 |

#### articles（記事）

| 列 | 型（想定） | 説明 |
|----|------------|------|
| id | uuid / text | 主キー |
| topic_id | uuid / text | 所属トピック |
| title | text | タイトル |
| url | text | 元記事 URL（重複判定の鍵） |
| summary | text / null | AI 要約 |
| importance | text / null | `high` / `medium` / `low` など |
| is_read | boolean | 既読フラグ |
| published_at | timestamptz / null | 公開日時 |

### 6.3 補足（フロントのみの記憶）

| 保存先 | キー | 内容 |
|--------|------|------|
| localStorage | `rss-app.topic-feed-urls` | トピック ID → RSS URL の対応表 |

将来は `topics.feed_url` への移行を想定する。

## 9. セキュリティ方針

1. **鍵の分離**  
   - フロント: `NEXT_PUBLIC_SUPABASE_*`（anon）のみ  
   - バック: `SUPABASE_SERVICE_ROLE_KEY` / `OPENAI_API_KEY`（秘密）  

2. **RLS**  
   - Supabase で RLS を有効化し、必要な SELECT / INSERT / UPDATE ポリシーを設定する  
   - 現状は開発向けの広い許可を想定（本番では絞る）  

3. **ブラウザに出さないもの**  
   - service_role キー  
   - OpenAI API キー

## 11. 制約・既知の前提

1. ログイン機能はなく、鍵と RLS でアクセスを制御する  
2. RSS URL は DB ではなくブラウザ記憶（暫定）  
3. AI キー未設定時は要約フォールバック（重要度 `low`）でパイプラインを止めない  
4. キュレート失敗時、フロントはメッセージ帯で理由を表示する
